# omp-dispatch 需求

- REQ-1 "Dispatch delivers GitHub issue graphs through durable tickets that move along a configurable workflow state machine, with source-confirmed effects, one-shot seat sessions, and fresh independent judges."
- REQ-2 "Main chooses which independent tickets run concurrently and which dependency edges enforce serial delivery; the workflow decides what happens to each ticket on the way."
- REQ-3 "A coordinator starts from the issue it delivers, never from a switch inside a session."
- REQ-4 "`cwd` is where the coordinator runs; `frontend` names where its process runs, and every field besides `kind` belongs to that frontend. Unknown fields at either level are refused, so a frontend's options extend the link without changing its path or query grammar."
- REQ-5 "The launcher holds no state of its own. It reads the link, calls the named frontend, and returns one page naming exactly one outcome: `launched`…`existing` (the frontend already runs a coordinator for that exact reference and started nothing), `rejected` (malformed path or number, a missing, malformed or unknown `spec`, a `cwd` that is not an existing absolute directory, or a request that is not a user's click navigation), or `frontendFailed` (the frontend's own output)."
- REQ-6 "The Tern frontend opens a tab running the coordinator, or focuses the live block that already runs that exact reference."
- REQ-7 "…it opens a window in `cwd` first whenever no window client is connected: a block started without one would run invisibly."
- REQ-8 "Launches of one reference, from clicks and deliveries alike, run one after another, so a launch that arrives while another is still starting the same coordinator ends `existing` on the block that one started rather than opening a second tab."
- REQ-9 "…`uninstall` removes it and `status` reports it together with the GitHub App and its webhook listener."
- REQ-10 "The launcher can also start a coordinator without a click, when a GitHub App delivers an `issues` event."
- REQ-11 "The App asks for read access to issues and subscribes to `issues` events."
- REQ-12 "Registering again replaces the file with a new App's credentials."
- REQ-13 "…accepting a delivery only when its `X-Hub-Signature-256` matches the App's webhook secret. It is a separate port from the link listener so that exposing it never exposes the click endpoint, whose header check a non-browser client could forge."
- REQ-14 "It judges the candidate texts in memory with the same schemas the coordinator applies at start…It reads and writes no Meerkat file, so an editor can refuse a save without starting a coordinator."
- REQ-15 "…which must name exactly those three files…"
- REQ-16 "A delivery starts a coordinator on the event that makes the trigger condition true, through the frontend and `cwd` of the link in the issue body; an issue without a valid link for itself never starts one. The condition needs an open issue whose author association is allowed…"
- REQ-17 Trigger mode `link` (default): "the body carries a valid launcher link for this issue"; events that can make it true: "`opened`, `reopened`, `edited` when the edit adds the link". Trigger mode `label`: "the link, and a label from `githubTriggerLabels` (any label when empty)"; events: "the above, and `labeled` when the added label is the first match".
- REQ-18 "`githubTriggerAssociations` (default `OWNER,MEMBER,COLLABORATOR`) lists the issue author associations GitHub reports that may start a coordinator; it describes the issue's author, not who labeled or edited it."
- REQ-19 "The trigger settings and the App credentials are read on every delivery; `webhookHost` and `webhookPort` are read when the launcher starts…"
- REQ-20 "The launcher reads the user-level plugin settings, not a project's `plugin-overrides.json`."
- REQ-21 "Every delivery is answered with its decision once made (`launching`, `ignored` with the reason, or a rejection) and logged to the launcher's log; the frontend launch continues after the answer."
- REQ-22 "`--dispatch` is the whole identity. From `session_start`, the process's Main coordinates that issue and keeps the same native session throughout delivery."
- REQ-23 "One visible startup message identifies the issue and lists its saved active agendas…or says…no saved active agenda; only a message that lists one tells Main to `resume`."
- REQ-24 "Ending a coordinator means ending its omp process."
- REQ-25 "Without the flag the extension registers nothing else: no active `dispatch` tool, no timers, no dispatch state."
- REQ-26 "All current parent sub-issues must be represented. Dependencies refer to ticket IDs; independent tickets have no edge."
- REQ-27 "Main can change the topology and record exceptional rulings with `resolve`…A saved active agenda is taken over with `resume` and its `agenda` id alone."
- REQ-28 "An agenda belongs to the issue that is its `parent` or the `issue` of any of its tickets. A coordinator sees only the active agendas that belong to its launch issue: they alone appear in the startup message, can be resumed, and refuse a new `convene` while one is saved."
- REQ-29 "Resuming any other agenda is refused with `ownershipBlocked` and changes neither its file nor the coordinator. Active agendas of other issues in the same data directory…stay as they are and do not keep this issue from being convened."
- REQ-30 "A coordinator that exits normally writes the agenda back to detached."
- REQ-31 "…only a process with that pid and the same start time is the previous coordinator, so a crashed or killed coordinator, or a pid since reused by another process, does not block it. While the previous coordinator still runs, `resume` refuses with `agenda_attached`, naming its pid and start time, and the agenda stays with that process."
- REQ-32 "Every ticket, and the parent closure once every ticket is delivered, moves through a state machine defined by the workflow. The workflow decides which states exist, what each one does, the condition for entering it, and where each outcome leads. Code fixes only what a state kind does and the source checks no workflow can switch off."
- REQ-33 "Installing this plugin supplies both agents without omp-config. Failing CI, a conflict, or a rejected review returns the ticket to `Coding`."
- REQ-34 "Neither packaged agent specifies a model. The host uses the current session model by default…"
- REQ-35 "A workflow's duties (`brief`) remain separate from the agent's base responsibilities."
- REQ-36 Kind `work`: "seats one `role`…the seat pushes a branch and calls `submit`; a later seat of the same role forks that role's session"; outcomes: "`submitted`, `escalated`".
- REQ-37 Kind `judge`: "seats every listed judge on a `subject`: `pullRequest` (the exact PR head) or `mergeCommit` (the exact merge commit); parent judges check out the first ticket's target branch"; outcomes: "`passed` (every judge passed; an empty list passes at once), `rejected` (any judge failed), `escalated`".
- REQ-38 Kind `action`: "performs one GitHub write and waits for GitHub to confirm it: `publishPr`, `merge`, `closeIssue`, `rerunChecks` (every failing Actions run of the PR; with none it escalates); parent: `closeParent`"; outcomes: "`done`".
- REQ-39 Kind `decision`: "moves to the first branch whose condition holds, re-checked on every refresh; an unconditional last branch…is its fallback, and without one it waits".
- REQ-40 Kind `final`: "delivered"; no outcomes.
- REQ-41 "An outcome leads to a state, to `escalate` (Main's ruling, the `Escalated` state), or to a branch list…whose first matching branch wins and whose last entry is the fallback. Any state may declare an entry condition…whichever outcome or ruling targets the state, the ticket enters it only while `when` holds, and goes to `otherwise` instead."
- REQ-42 "Conditions read only source-confirmed facts and the machine's own history…The parent machine has no PR, so it uses only `visits` and the combinators."
- REQ-43 "While the ticket holds an open PR in that state, `checksFailed`, `conflict`, `behind`, and `drift` (a new head, title, or description) lead where `observe` says, and to `escalate` when it says nothing. A PR that is closed, retargeted, a draft, or no longer closes exactly its issue, and checks that cannot be read, always escalate."
- REQ-44 "`ticket.initial` is the work state a convened ticket starts in, and the state Main launches. A ticket convened with `adoptPr` starts in…when the PR is open and…when it is already merged; it has not visited the initial state. `parent.initial` is entered once every ticket is delivered, and again whenever the delivered children change."
- REQ-45 "`merge` waits until the PR is mergeable with passing required checks and every dependency is delivered. It then needs a passed approval, on the current PR fingerprint, from every judge state named in `requires` and from every PR judge state the ticket still holds. A drift drops all PR approvals."
- REQ-46 "`closeIssue` needs a Main `noCode` ruling on the current contract, or a merge still contained in the target with its `requires` approvals. `closeParent` needs the current children fingerprint with its approvals."
- REQ-47 "a ticket stays in a final state only while its issue is closed and its merge or `noCode` ruling still holds. The parent closure stays in one only while the parent issue is closed and its children are the ones judged. Otherwise they escalate. Dependencies, the parent closure, and `finish` count a ticket as delivered when it rests in a final state."
- REQ-48 "these source checks bind Main's `resolve` too, but judge states do not. Main may resolve a ticket or the closure into a later state, including a final one, without its judges once the source facts hold; that is an explicit ruling, recorded on the ticket."
- REQ-49 "a judge state that did not pass keeps no approval. A GitHub write that fails or has an unknown outcome always escalates to Main."
- REQ-50 "every state entry starts a new ticket revision, so a seat of the previous entry is superseded. A state that completes at once…moves on immediately. A machine that passes 64 states without waiting escalates as a loop."
- REQ-51 "The loader refuses unknown fields, unknown targets, unreachable states, cycles of entry fallbacks, an initial state that is not an unguarded `work` state, a machine without a final state, a parent condition that reads the PR, a judge role used twice or shared with a work role, a work role with two agents, a `requires` naming the wrong kind of judge, a missing outcome, and the reserved names `escalate`, `Escalated`, `Asking` and `Replaced`."
- REQ-52 "A `brief` is the seat's duty. Dispatch adds the protocol to it: ticket scope, what the checkout is, the exact `submit` or `verdict` call, and that the workflow decides what follows. An `agent` is a native agent name, resolved the way `task` resolves it in the coordinator's `cwd`, and must be non-blocking."
- REQ-53 "`convene` reads the current…setting `workflowFile`, relative to the coordinator's `cwd`; an explicitly selected file must exist. `OMP_DISPATCH_WORKFLOW` takes precedence."
- REQ-54 "When neither the environment nor plugin setting selects a file, `convene` reads `<dataDir>/workflow.yml`, falling back to the built-in workflow when the file does not exist. An unreadable or invalid file, an empty/non-string setting, or an agent that cannot host a seat refuses `convene`."
- REQ-55 "The agenda freezes the workflow it was convened with: relays, rework, and `resume` never read the file again, so edits apply to the next `convene`."
- REQ-56 "Each is overridden by its environment variable whenever that is set, even to an empty value. Paths resolve against the coordinator working directory."
- REQ-57 "A blank `dataDir`, an interval that is not such a whole number (a decimal string such as `"30"` counts), or a non-string value refuses to start the coordinator; the notification names the setting or environment variable and its value."
- REQ-58 "Notifications, command help, and the launcher CLI and HTML use English or Chinese. On each text generation, language is resolved from normalized `OMOMP_LANG=en|zh`, then the first nonempty `LC_ALL`, `LC_MESSAGES`, or `LANG` (`zh` prefix means Chinese), then English."
- REQ-59 "The agent-directory omomp files never participate in language resolution."
- REQ-60 "Model-facing tool descriptions, results, workflow briefs, and coordinator instructions stay English."
- REQ-61 "Runtime notifications show a localized error category and point to the log for the full structured protocol diagnostic."
- REQ-62 "Main decides only when each ticket is launched. `status` returns the agenda, including its workflow, with the `launchable` tickets (never launched, neither `Escalated` nor delivered, every dependency delivered), the `asking` tickets (each with its worker's question, the id of its `ask` comment once GitHub shows it, and the council `agenda` once the ask was escalated there…), and the seats currently `seated`."
- REQ-63 "Main calls `launch`…once per ticket; an omitted `role` means the ticket's currently executable seats, and a given `role` must be one of them. The call marks the ticket started, seats its current state at once, and returns their native async job IDs, so independent tickets can be launched back to back."
- REQ-64 "From then on Dispatch follows the workflow by itself: it seats each work and judge state, performs each action, and evaluates each decision, including the parent machine once every ticket is delivered."
- REQ-65 "A seat is one-shot per revision: a role seated at a revision is never seated at that revision again within the process, so a seat that ends without a handoff is followed by its escalation, not by a replacement. A work seat starts only after every seat of its ticket has exited."
- REQ-66 "Main is woken by a `dispatch-attention` message only for a decision it has not yet been told about and that is still open when its current turn ends: a ticket that became launchable, an `Escalated` ticket or closure (keyed by revision), a failed Meerkat effect…or a finished agenda awaiting `finish`. A decision Main settles within the turn that produced it…never wakes it again. Launching, running seats, seat job completions, a ticket waiting in `Asking`, and effects in flight do not notify."
- REQ-67 "Each seat reads only its bound ticket…A work seat pushes its code branch and calls `submit` with the ticket revision, branch, head, title, and a PR body closing exactly that issue. A judge calls `verdict` with its own `role`; findings land on the ticket's notes."
- REQ-68 "A seat calls `escalate` for a question, blocker, proposed split, or no-code finding, which follows its state's `escalated` outcome; only a `question` may carry a `tier` (`simple` or `complex`)."
- REQ-69 "A successful handoff ends the seat; it does not wait for another assignment."
- REQ-70 "A seat that ends at its current revision without a handoff, or cannot be started, escalates its ticket instead of being relaunched."
- REQ-71 "A resolution starts a new revision, so the seats of the state it replaces are superseded; the one exception is an `Asking` ticket resolved to `Asking`, which seats nobody and keeps its revision and question."
- REQ-72 "`resolve` records a persistent ruling, synchronizes the issue contract, adjusts topology, adopts source results, or settles a failed or uncertain effect."
- REQ-73 "`retry` adopts the effect if GitHub already shows it. Otherwise a Meerkat record…or a request to the intent guardians…is queued again under the same effect and sent once more, and any other effect is cancelled: resolving to its action state requests it afresh. A `publishPr` or `rerunChecks` can be retried that way directly. A `merge` or `closeIssue` cannot: the ruling changes the fingerprint its judges approved, so it has to go back through those judge states."
- REQ-74 "The target is entered through its entry condition, and `resolve` is refused when that entry escalates…"
- REQ-75 "Main confirms no-code work with `noCode` and a `to` whose entry lands in a `closeIssue` action state or a final state; the ticket is delivered only after GitHub confirms the closure."
- REQ-76 "`resolve` may queue only `replaceBody`, `createIssue`, `attachChild`, and `rerunChecks` for a ticket, and nothing for the closure; publishing, merging, and closing belong to the workflow's action states."
- REQ-77 "A started ticket resumes its relay from the named state. A changed `target` drops the ticket's work sessions, so the next work seat checks out the new target."
- REQ-78 "`finish` records the final summary only after every ticket and the parent closure rest in a final state. A parent final state also needs the parent issue closed."
- REQ-79 "…seats never clone from the network."
- REQ-80 "A work role's first seat receives a new persistent native session and a checkout of the target branch; the ticket records that role's accepted session…A later seat of the role forks it…in the same checkout, repairing an interrupted transcript tail and resetting inherited cost…"
- REQ-81 "A role's first seat records its base system prompt and its tool presentation…The fork restores both and explicitly inherits the provider prompt-cache key. It clears the inherited todo list and appends only the incremental notes and rulings to the new turn. A fork source whose contract lacks the tool presentation cannot be forked, so its ticket escalates."
- REQ-82 "Every seat is a full native omp session in its checkout, not a restricted one. It binds the extensions Main loaded…reads the workspace's settings, discovers the workspace's custom tools, shares Main's MCP servers, and keeps every tool those provide…"
- REQ-83 "Only the seat's own session is bound to its ticket…helpers it spawns have their own native identities and are refused as seats. Seats run headless, so tool approvals are not prompted, and they never join IRC: a seat reaches Main only through its ticket."
- REQ-84 "Extensions bind from Main's process rather than being rediscovered, so project-local extensions or MCP servers of a different target repository are not loaded into its seats."
- REQ-85 "Judge seats always receive new blank sessions; their histories are never reused or forked."
- REQ-86 "`pullRequest` judges check out exactly the PR head their gate stamp names…so fork heads work…`mergeCommit` judges check out exactly the merge commit, and parent judges check out the first ticket's target branch; the host verifies the checkout's `HEAD` before the seat starts."
- REQ-87 "A parent judge's brief carries the closure record (its children's issues, terminals and targets, rulings and notes), not the parent or child issue bodies, and its checkout covers only that one target even when the children span several."
- REQ-88 "A superseded seat ends at its next native tool-completion boundary instead of retrying another revision's work; accepted handoffs finish normally so their checkpoints remain intact."
- REQ-89 "`mergeCommit` fingerprints pin the ticket's merge commit and freshly verify target containment, so unrelated forward merges do not invalidate a running verification."
- REQ-90 "Seat sessions are disposed when their native async jobs finish. Work checkouts survive process restarts and rework until `finish`; judge worktrees are removed when their jobs end."
- REQ-91 "Accepted transitions and effect intents are durably saved…before returning. Every external GitHub write first persists `executing`, performs the operation, then confirms its result through a fresh GitHub read. An unknown outcome becomes `uncertain` and is never automatically resent. Resume reconciles interrupted executing GitHub writes against GitHub rather than replaying them. A failed or uncertain workflow effect escalates its ticket."
- REQ-92 "Meerkat record effects…never escalate their ticket or supersede its seats, because they are written while a work seat may still be running: an uncertain one is confirmed by the next complete GitHub read that shows it and turns failed when that read does not, and a failed one keeps its error text, wakes Main…and blocks `finish` until Main settles it through `resolve` (`retry` sends the same record again unless GitHub already shows it, `adopt` takes what GitHub shows, `cancel` drops it; resolving to a work state seats a new work session, which writes its own marker and, if needed, the Status again, and resolving to `Done` requests the done Status again)."
- REQ-93 "A re-sent record is idempotent by its marker key or field value: the executor confirms one GitHub already shows instead of writing it twice."
- REQ-94 "A request to the intent guardians…is the one effect confirmed by its own answer rather than a GitHub read, because the guardians accept a repeat of it: a connection error or any answer other than 202 or 200 fails it with that text, never leaves it uncertain, and does not escalate the ticket; a request a restart interrupted is sent again on resume, and a failed one is sent again when Main resolves the ticket to `Asking` with `retry` on it."
- REQ-95 "Every effect records the state entry that requested it. A ready effect is cancelled once that entry is left, and a late confirmation records its result without moving a newer state. PR head, target, issue contract, PR body, or ruling changes invalidate approvals before any merge."
- REQ-96 "Older formats are rejected without migration or deletion."
- REQ-97 "The extension never rewrites conversation history or injects per-turn hidden ticket context; ticket reads and visible notifications are ordinary messages."
- REQ-98 "Empty leaves Meerkat integration off: Dispatch reads no Meerkat file, writes no Meerkat comment or Project field, and asks no intent guardians."
- REQ-99 "When it is set, the coordinator reads three YAML files at startup. A missing file, a missing key, a value of the wrong type, or a key the file does not define refuses to start the coordinator; the notification lists every problem as `<file>: <key path>: <problem>`."
- REQ-100 "With Meerkat integration on, every work seat that starts, fresh or forked for rework, leaves one comment on its ticket's issue whose last line is the `impl` marker `<!-- meerkat:impl {"v":1,"host":…,"pid":…,"agenda":…,"session":…,"file":…} -->`…"
- REQ-101 "When a work seat starts while the issue's item in the configured Project does not show the `inProgress` Status option, the item moves to it (the issue is added to the Project if it has no item there); when the ticket enters the final state `Done`, it moves to the `done` option."
- REQ-102 "Both writes are effects like the workflow's own: each is persisted before it is sent and counts as done only when a fresh GitHub read shows a comment with that marker kind and session, or that Status option."
- REQ-103 "Issue reads then also return every comment that ends in a `meerkat:` marker (`impl`, `ask`, `reply`, `replaced`, `escalated`, each with `"v":1` and all fields of its kind) and the issue's Project item; a malformed marker is logged and ignored."
- REQ-104 "When an Owner calls `escalate` with kind `question`, the ticket enters the built-in state `Asking` instead of its state's `escalated` outcome: it gets a new revision, seats nobody, and does not wake Main."
- REQ-105 "Its `ask` records the question, the tier (the one the seat gave, else `defaultTier`), the asking session's id and file, the work state it asked from, and the id of its `ask` comment."
- REQ-106 "Dispatch stops the asking session right after the handoff, so its transcript ends with that abort and no further assistant message."
- REQ-107 "The question is then written verbatim to the issue as a comment whose last line is `<!-- meerkat:ask {"v":1,"tier":…,"session":…} -->`, one per asking session."
- REQ-108 "Once GitHub shows that comment, its id is recorded and the intent guardians at `guardiansURL` receive `POST /v1/asks` with `{"issue":"owner/repo#n","comment":<id>,"question":…,"tier":…}`."
- REQ-109 "A failed request wakes Main…and leaves the ticket `Asking`. Main sends it again with `resolve` to `Asking` and `retry` on that effect, which keeps the question and its revision. `resolve` can also move an `Asking` ticket to any workflow state, which drops its question. Only a ticket already `Asking` can be resolved to `Asking`."
- REQ-110 "A work seat's brief under Meerkat integration explains the tier with `tierHelp` and says that asking ends the session."
- REQ-111 "A blocker, split or no-code finding, a judge's question, and every escalation with Meerkat integration off still go to Main as `Escalated`."
- REQ-112 "An ask is settled on its issue, by the guardians or the council, and every recompute reads it there. Only comments posted after the ask comment can settle it…a settlement on an earlier comment answered an earlier ask and is passed over without a note."
- REQ-113 "Among the later ones, the first `reply` (`<!-- meerkat:reply {"v":1,"ask":<id>,"decision":…} -->`) or `replaced` (`<!-- meerkat:replaced {"v":1,"ask":<id>,"by":"owner/repo#n"} -->`) marker whose `ask` is the recorded ask comment id settles it."
- REQ-114 "A reply returns the ticket to the work state it asked from, at a new revision, and notes the answering comment. Its Owner is forked from the asking session, so it keeps that transcript, and its first new message is `resumePrompt`, a blank line, and the reply comment's text above the marker, followed by the usual continuation for the new revision. A ticket whose asking state cannot be determined is escalated to Main instead."
- REQ-115 "A replacement ends the ticket in the built-in final state `Replaced`, naming the replacing issue: it seats nobody, opens no PR, keeps its sessions, and counts as delivered for dependencies, the closure and `finish`."
- REQ-116 "An `escalated` marker (`<!-- meerkat:escalated {"v":1,"ask":<id>,"agenda":…} -->`) only records the council agenda on the ask, which `status` shows; the ticket stays `Asking` until a reply or replacement follows."
- REQ-117 "A later settlement marker naming another ask, or none, settles nothing and is noted once on the ticket as `ignored settlement <comment> for ask <id|none>`."
- REQ-118 "Each delivery scenario also checks that Main launched every ticket exactly once, was never woken for a decision it had already taken, that every expected judge's accepted verdict sat on the exact commit its subject names, and that the simulated repository ends in the expected state. A scenario without Meerkat integration also checks that no issue carries a `meerkat:` comment and the Project has no item."
- REQ-119 Scenario `mcp-scope`: "`A`'s next request after the load presents `mcp__fx_added` and calls it, and the call returns the server's result, while no later request of Main or of any other seat presents it." and "…its session contract lists `dispatch` once."
