# omp-dispatch 需求

- REQ-1 "Dispatch delivers GitHub issue graphs through durable tickets driven by a programmatic workflow state machine, with source-confirmed effects, isolated role-pure seats, orthogonal independent judges, and an on-demand Fallback Arbiter."
- REQ-2 "The programmatic Workflow Controller constructs the execution DAG from the GitHub issue graph and hidden sub-issue metadata, automatically launches tickets as dependencies complete, drives every normal state transition, and completes delivery without AI involvement on the happy path."
- REQ-3 "A coordinator starts from the issue it delivers as a dedicated Tern Dispatch Pane process, never as a raw chat session or mode switch inside an interactive agent session."
- REQ-4 "`cwd` is where the coordinator runs; `frontend` names where its process runs, and every field besides `kind` belongs to that frontend. Unknown fields at either level are refused, so a frontend's options extend the link without changing its path or query grammar."
- REQ-5 "The launcher holds no state of its own. It reads the trigger target, calls the named frontend, and returns one outcome: `launched`, `existing` (the frontend already runs a coordinator for that exact reference and started nothing), `rejected`, or `frontendFailed`."
- REQ-6 "The Tern frontend opens a dedicated Dispatch Pane for the issue, or focuses the live Dispatch Pane that already runs that exact reference."
- REQ-7 "When no Tern window client is connected, the Tern frontend opens a window in `cwd` before creating the Dispatch Pane so delivery never runs invisibly."
- REQ-8 "Launches of one reference, from manual clicks and webhook deliveries alike, are serialized so a concurrent launch resolves as `existing` on the pane already starting rather than opening a duplicate pane."
- REQ-9 "Launcher management supports install, uninstall, and status reporting covering the local listener, the GitHub App registration, and its webhook listener."
- REQ-10 "Dispatch supports dual trigger ingress: manual triggering via a clickable link (local HTTP badge link and OS/Tern URL scheme) and automatic triggering via a GitHub App `issues` webhook."
- REQ-11 "The GitHub App requests read access to issues and subscribes to `issues` events."
- REQ-12 "Registering the GitHub App again replaces the stored credentials with the new App's credentials."
- REQ-13 "The webhook listener binds a separate port from the manual click listener and accepts a delivery only when its `X-Hub-Signature-256` signature matches the App's webhook secret."
- REQ-14 "The configuration check endpoint validates candidate Meerkat configuration texts in memory against the same schemas the coordinator applies at start, without reading or writing configuration files."
- REQ-15 "The configuration check endpoint requires exactly the three Meerkat configuration files (`shared/repos.yaml`, `shared/project.yaml`, `dispatch/delivery.yaml`)."
- REQ-16 "A webhook delivery starts a coordinator on the event that makes the trigger condition transition from false to true for an open issue whose author association is allowed."
- REQ-17 "Label-gated auto-triggering requires an open issue carrying an allowed dispatch label and resolves its local repository workspace from configured `repoWorkspaces` (or Meerkat repository mapping) without requiring a loopback link inside the issue body."
- REQ-18 "Trusted author associations restrict which issue authors may auto-trigger delivery via the GitHub App."
- REQ-19 "Trigger settings and App credentials are read on every webhook delivery; listener bind addresses are read when the launcher starts."
- REQ-20 "The launcher reads user-level plugin settings rather than project-local overrides."
- REQ-21 "Every webhook delivery is answered immediately with its decision (`launching`, `ignored`, or `rejected`) and logged, while frontend launch proceeds asynchronously."
- REQ-22 "The Tern Dispatch Pane renders a live native graphical overview of the delivery: issue DAG progress, active and completed seat cards with nested helper telemetry, star-topology transition and handoff logs, and a steering dock wired exclusively to the Fallback Arbiter."
- REQ-23 "The Dispatch Pane spawns and manages isolated top-level `omp` seat panes in Tern's background parking deck, supporting one-click unpark/focus inspection, live transcript peek, and post-handoff pane cleanup while preserving resumable session files."
- REQ-24 "Ending a coordinator cleanly detaches its active agenda and disposes running seat sessions."
- REQ-25 "Sub-issues may carry single-line hidden metadata comments (`<!-- dispatch:meta {...} -->`) specifying designated subagent, model, fork mode, harness, target, or dependencies; Dispatch parses and validates these parameters deterministically at ingest."
- REQ-26 "Every current parent sub-issue must be represented in the agenda DAG; dependencies refer to ticket identities and independent tickets run concurrently up to configured concurrency limits."
- REQ-27 "Programmatic DAG compilation validates dependency acyclicity, dangling references, integration sink presence, contract structure, prose-vs-metadata dependency consistency, capability availability, and stance-safe fork selection before launching any seat."
- REQ-28 "An agenda belongs to its parent issue or any of its ticket issues; a coordinator sees and resumes only active agendas belonging to its launch issue."
- REQ-29 "Resuming an agenda belonging to another issue is refused without modifying that agenda's state file."
- REQ-30 "A coordinator that exits normally writes its agenda back to detached."
- REQ-31 "Resuming an attached agenda checks live OS process identity (pid and start time); a live holder refuses takeover, while a crashed or reused pid permits recovery."
- REQ-32 "Every ticket and parent closure moves through a configurable workflow state machine whose state kinds and source invariants are enforced programmatically by the Workflow Controller and Seat Bridge."
- REQ-33 "Packaged work and judge agent profiles work out of the box without requiring separate external configuration, and model bindings remain configurable per agent or per sub-issue metadata."
- REQ-34 "Compile-time graph defects transition the agenda to `ConveneEscalated` with zero work seats launched and wake the Fallback Arbiter to repair the authoritative GitHub issue graph until the deterministic graph compiler passes with zero diagnostics."
- REQ-35 "GitHub issue and sub-issue contracts remain the authoritative single source of truth for the delivery graph; Fallback graph mutations update GitHub first and pass compiler verification before advancing the agenda graph epoch."
- REQ-36 "Kind `work`: seats a work role in an isolated worktree to implement and verify the ticket contract and hand off through the Seat Bridge."
- REQ-37 "Kind `judge`: seats orthogonal independent judges (`ContractVerifier` for narrow low-risk tickets, or black-box `AcceptanceJudge` plus white-box `CodeReviewJudge` for higher-risk/integration tickets) on the exact source subject (`pullRequest`, `mergeCommit`, or `parent`)."
- REQ-38 "Kind `action`: performs one source-confirmed GitHub write (`publishPr`, `merge`, `closeIssue`, `rerunChecks`, `closeParent`), retrying transient external failures with bounded backoff before escalating."
- REQ-39 "Kind `decision`: branches deterministically on source-confirmed facts and machine history (`checks`, `mergeable`, `visits`, boolean combinators), requiring verified local test execution when branch protection configures zero required CI checks."
- REQ-40 "Kind `final`: delivered."
- REQ-41 "Workflow rework loops are bounded by explicit visit limits so repeated rejection or persistent CI failures escalate to the Fallback Arbiter instead of cycling indefinitely."
- REQ-42 "Conditions evaluate only source-confirmed facts and durable machine history; parent machine conditions cannot read PR-only predicates."
- REQ-43 "Non-normative prose or typo edits to an issue body reconcile in place against the semantic contract digest without aborting active seats; normative contract changes invalidate stale approvals."
- REQ-44 "A ticket with an adopted PR starts at the configured adopted entry state; parent closure enters automatically once every ticket is delivered and re-enters whenever delivered children change."
- REQ-45 "Merging waits until dependencies are delivered, the PR is mergeable with passing required checks (or verified local checks), and every required judge approval matches the current head and normative contract."
- REQ-46 "Closing a ticket requires a verified merge contained in the target with required post-merge approvals (or an explicit Fallback terminal settlement); closing the parent requires current children approvals."
- REQ-47 "A ticket stays delivered only while its issue remains closed and its merge containment holds; otherwise reconciliation re-opens escalation."
- REQ-48 "The Fallback Arbiter handles escalations through typed operational or normative resolutions; every ruling is durably recorded on the ticket."
- REQ-49 "A judge state that rejects or escalates keeps no approval; a workflow GitHub write whose outcome remains failed or uncertain after bounded retries escalates to the Fallback Arbiter."
- REQ-50 "Every state entry or graph epoch bump supersedes prior seat revisions; a machine that traverses 64 states without waiting escalates as a loop."
- REQ-51 "The workflow loader validates all state references, reachability, guard acyclicity, role uniqueness, judge-requirement subject types, and reserved state names."
- REQ-52 "A seat's constitutional stance and workflow duty are assembled by the Seat Bridge without dumping raw cross-seat prose history."
- REQ-53 "Workflow configuration resolves from explicit environment override, plugin setting, data directory file, or the built-in workflow, and freezes on the agenda upon convene."
- REQ-54 "Invalid workflow files or unavailable configured seat agents refuse agenda creation with concrete diagnostics."
- REQ-55 "Runtime graph collisions between parallel tickets are detected via live touch-set monitoring and ephemeral-index merge checks, suspending only the follower ticket into `SuspendedOnGraph` while keeping the leader running."
- REQ-56 "Suspending a seat into `SuspendedOnGraph` preserves its worktree overlay and immediately captures an ephemeral context manifest while its provider KV cache is warm, preventing progress loss during dependency reordering, ticket coalescing, or splitting."
- REQ-57 "Coalescing indivisible coupled tickets merges their contracts into the primary ticket and requires the resulting PR to close every coalesced issue via merged code provenance."
- REQ-58 "Notifications, command help, and launcher CLI/HTML support English and Chinese based on locale settings."
- REQ-59 "Model-facing tool descriptions, results, workflow briefs, and Fallback instructions remain in English."
- REQ-60 "Runtime notifications show a localized error category and point to logs for full structured diagnostics."
- REQ-61 "The native `omp` runtime (`OMP Seat Host`) is the primary implementation supporting all seven `omomp` fork modes, immutable prefix KV-cache preservation, and out-of-process top-level `session_stop` non-stop enforcement."
- REQ-62 "External agent runtimes (such as Claude Code, Codex, and other CLIs) are routed behind a dedicated `OAR Seat Host` adapter targeting `botiverse/oar`, explicitly deferred beyond Phase 1 so the native `omp` host remains uncompromised."
- REQ-63 "Every seat runs with hard per-role tool pruning and role-split transition tool injection through the Seat Bridge: Work seats receive only work handoff/escalation tools, Judge seats receive read-only inspection and verdict/escalation tools, and only the Fallback Arbiter receives resolution and unimplemented-declaration tools."
- REQ-64 "Strict star-topology isolation forbids direct communication between different seats; peer-to-peer channels are disabled and all cross-seat coordination flows solely through the Workflow Controller and Fallback Arbiter."
- REQ-65 "Stance and intent preservation enforces an information firewall: Judges never receive Coder self-justification prose or prior reviewer narratives; black-box acceptance judges run against the runnable checkout without inspecting `git diff`, while white-box code reviewers inspect diffs in a read-only environment; rework seats receive only structured defect items and normative rulings."
- REQ-66 "Context transitions avoid both in-session role-switch KV cache invalidation and redundant cold-start codebase re-reading by keeping each seat's `[system prompt + wire toolset]` immutable from turn 1 and selecting the appropriate `omomp` fork mode per transition (replica fork for same-model scout-to-implement, ephemeral warm manifest for cross-model/suspended handoffs, contract-preserving rework fork with elision for rework, cut-point fork for rollback, tangential clone for 1-hop tactical helpers, never forking work history into judges)."
- REQ-67 "Work seats may spawn at most bounded 1-hop tactical helpers without inheriting seat transition credentials; Judge seats cannot spawn subagents."
- REQ-68 "The Fallback Arbiter is empowered to resolve fundamental delivery issues autonomously, including rewriting flawed issue acceptance scope, repairing broken GitHub issue graphs, injecting blocking prerequisite repair tickets for out-of-scope upstream or CI defects, and re-routing seats across models, fork modes, or rollback points."
- REQ-69 "A seat that finishes a valid handoff terminates cleanly without waiting for another assignment."
- REQ-70 "Provider rate limits or quota exhaustion trigger supervised backoff and session resume rather than aborting the seat into escalation."
- REQ-79 "Every seat checkout is a detached git worktree derived from a per-repository bare cache; seats never clone directly from the network."
- REQ-80 "Work role sessions persist across rework and suspension so later seats of the same role fork their prior session in the same checkout with interrupted-tail repair and inherited-cost reset."
- REQ-81 "Work seats record their immutable base system prompt and wire tool presentation in a session contract entry so rework forks restore identical prefixes and inherit the provider prompt-cache key."
- REQ-82 "Judge seats never inherit work-role conversation history; independent judge runs may share only a static read-only constitutional prefix."
- REQ-83 "Judge worktrees check out the exact commit named by their gate stamp (PR head, merge commit, or parent target) and verify `HEAD` before starting."
- REQ-84 "Superseded seats are aborted promptly when their ticket revision or agenda graph epoch advances."
- REQ-85 "Work checkouts survive restarts and rework until completion; judge worktrees are removed when their jobs end."
- REQ-91 "Accepted transitions and effect intents are durably saved before returning. Every external GitHub write first persists `executing`, performs the operation, then confirms its result through a fresh GitHub read. An unknown outcome becomes `uncertain` and is never automatically resent. Resume reconciles interrupted executing GitHub writes against GitHub rather than replaying them."
- REQ-92 "Meerkat record effects (`comment`, `setProjectField`) do not escalate tickets or supersede running seats; uncertain records confirm or fail on the next complete GitHub read, and failed records surface to the Fallback Arbiter."
- REQ-93 "Re-sent Meerkat records are idempotent by marker key or field value."
- REQ-94 "Requests to Meerkat intent guardians confirm directly on HTTP 200/202, replay safely on restart, and leave the ticket in `Asking` on transient failure."
- REQ-95 "Every effect records the state entry that requested it; leaving that entry cancels ready effects, and late confirmations never advance a newer state."
- REQ-96 "Older incompatible state envelope formats are rejected without silent migration or deletion."
- REQ-98 "Leaving Meerkat configuration unset disables all Meerkat reads, writes, and guardian asks."
- REQ-99 "When Meerkat configuration is set, invalid or missing configuration files refuse coordinator startup with per-key diagnostics."
- REQ-100 "With Meerkat integration on, each started work seat writes an `impl` marker comment and updates the configured Project status to in-progress, moving to done on final delivery."
- REQ-104 "With Meerkat integration on, a work seat question enters `Asking`, posts an `ask` marker comment, notifies the intent guardians, and resumes via forked session on `reply` or ends `Replaced` on `replaced`."
- REQ-120 "Three-layer headless non-stop enforcement forbids any active seat from exiting normally before the Seat Bridge accepts a valid handoff (`submit` or `verdict`) or an admissible escalation (`escalate`) for its bound contract and epoch; premature turn exits are blocked by the native stop hook rather than silently abandoning the ticket."
- REQ-121 "Fallback rulings are action-typed: an operational resolution (such as retrying a failed GitHub write, re-running checks, re-routing a seat, or adding a repair dependency) preserves existing Judge approvals on the unchanged normative contract and head, whereas a normative resolution (such as rewriting issue acceptance criteria or adding a normative ruling) updates the normative contract digest and invalidates approvals recorded under any prior normative contract so no merge proceeds on stale approvals."
- REQ-122 "Only the Fallback Arbiter holds authority to declare a ticket unimplemented. Low-level engineering faults—including broken CI, flaky tests, upstream code bugs, merge conflicts, or tool/environment errors—are categorically rejected as grounds for seat escalation surrender or unimplemented declaration (in-repo faults must be fixed directly by the Work seat; out-of-scope faults must trigger a repair ticket). Unimplemented settlement is accepted only for a genuine external or architectural impossibility after exhausting distinct verified alternatives."
- REQ-123 "Escalations are tracked in a level-triggered pending set so the Fallback Arbiter cannot silently drop an unresolved escalation, and every normative or graph resolution advances the epoch so stale calls from superseded seats are rejected by the Seat Bridge."
